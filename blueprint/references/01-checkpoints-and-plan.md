# 检查点与开发计划

MAIN 维护一个 `DEVELOPMENT_PLAN.md`。已有等价计划时，先确定单一权威文件并链接它。每次开始或完成任务、遇到缺陷、调整依赖、改变范围、更新决策或收到审批，都更新计划。同一检查点复审时保留被否决或作废的决定与原因。

## 七个开发阶段

| 阶段 | 主责 | 进入和退出条件 |
| --- | --- | --- |
| 1. 产品发现 | MAIN | 核对仓库、用户旅程、页面与窗口、必需与可选范围、平台和验收。完成 CP0。 |
| 2. 架构与可行性 | Electron、MAIN | CP0 获批后，核对进程、数据、IPC、安全、分发和依赖。完成 CP1。 |
| 3. 视觉方向 | Taste、Impeccable | CP1 获批后，准备代表性桌面屏和有依据的视觉方向。完成 CP2。 |
| 4. 设计系统与详细计划 | Impeccable、MAIN | CP2 获批后，明确组件、token、状态、实现映射、依赖图和验收单。完成 CP3。 |
| 5. 分里程碑实现 | Electron、MAIN | CP3 获批后，按可验证任务实施、运行、自查和交接。在 CP4 核对依赖及变更。 |
| 6. 实际运行与审查 | agent-browser、Impeccable、Taste | 运行真实应用，复现并记录缺陷。修复、复测、更新 QA 证据与未验证项。 |
| 7. 发布验收 | Electron、MAIN | 汇总功能、架构、设计、QA、回归、安全、包级验证和限制。完成 CP5。 |

回归验证贯穿影响到代码或应用行为的阶段。共享导航、组件、权限、IPC、数据、窗口、鉴权和核心路径发生变化时，用依赖图确定受影响的既有用例。

## 决策检查点

| 检查点 | 供审阅的材料 | 决策 |
| --- | --- | --- |
| CP0 产品范围 | 用户与目标、必需／可选／后续事项、用户旅程、页面与窗口、假设、疑问、初始里程碑与验收 | 用户明确批准后进入详细设计。 |
| CP1 技术架构 | 技术选择与替代方案、进程和信任边界、IPC、数据、分发、可行性证据和依赖 | 用户明确批准后进入视觉方向。 |
| CP2 视觉方向 | 代表屏、参考依据、与产品及桌面环境的契合、状态与一致性规则 | 用户明确批准后展开设计系统。 |
| CP3 设计与计划 | 设计系统、代表 UI、组件到模块的映射、里程碑、依赖、复杂度、风险、测试和完成条件 | 用户明确批准后实现。 |
| CP4 实现里程碑 | 已验证结果、相关回归、后续依赖、风险与变更 | 在已批准边界自主推进。超出范围、重大架构变化或重要设计变化提交用户批准。 |
| CP5 QA 与发布 | 完成报告、功能矩阵、架构与设计审查、安全、运行 QA、回归、打包与已知限制 | 用户明确批准后记录最终验收。 |

为每个检查点记录目标、已完成事项、决定、交付物、未决项、风险、验收标准、证据、下一阶段计划及审批状态。使用 `NOT_STARTED`、`IN_PROGRESS`、`BLOCKED`、`READY_FOR_REVIEW`、`APPROVED`、`REJECTED`、`COMPLETED`。呈审材料齐备时标记 `READY_FOR_REVIEW`。需要用户批准的检查点以明确回复作为 `APPROVED` 的证据。记录批复的日期或消息来源与版本。通过退出条件后再记录 `COMPLETED`。

## 执行与重排

- 将任务绑定需求、责任人或 Skill、依赖、改动模块、预期输出、可观测验收、验证方法、风险和状态。例如把窗口、路由、快捷键与窗口尺寸适配分成可分别验证的任务。
- 前置任务未满足验收时，保持依赖项为待办或阻塞。只有在授权和文件所有权清晰时并行推进独立任务。
- 新信息推翻计划时，停止受影响工作，记录原因、影响、依赖变化与新的复杂度。将涉及范围、预算、架构或重点视觉方向的改变送回最近受影响的检查点审批。
- 使用现有 `PRODUCT.md`、`DESIGN.md`、架构文档及 QA 记录的等价位置。既有批准要有可核对的来源，缺失信息保留为未决。
